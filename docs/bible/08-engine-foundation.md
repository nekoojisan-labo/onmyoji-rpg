# 要件定義書: A 基盤層（A1 レンダリング基盤 / A2 移動・操作・カメラ / A3 ワールド・シーン管理・セーブ）

## A1. レンダリング基盤

### 目的 / スコープ
Three.js 上に「2D画像を板ポリに貼って3D空間へ立てる」フル2.5Dビルボード描画の土台を敷く。MMORPG風の見た目（広い世界・多数NPC同時表示）を、3Dモデルゼロ・全アセット画像という制約のまま、深度の破綻なく・60fps目標で成立させる。和風ダークの空気（霧・最小限のライティング・接地影）を共通描画ルールとして固定する。A2/A3はこの描画契約の上に乗る。

### 詳細要件

#### A1-1. シーングラフ構成
- ルートは単一 `THREE.Scene`。直下を以下のグループに固定分割し、描画順とz-sortの責務を分離する。
  - `worldGroup`: 地面（床テクスチャを貼った水平板）・静的構造物ビルボード・装飾。
  - `entityGroup`: 動く/動かないキャラ系ビルボード（プレイヤー・式神・NPC・敵・拾得物）。深度ソートの主対象。
  - `fxGroup`: 呪術エフェクト・斬撃・被弾フラッシュ・パーティクル。
  - `shadowGroup`: 接地影（後述、本物の影マップは使わない方針）。
- レンダラ: `WebGLRenderer({ antialias:true, powerPreference:'high-performance' })`。`renderer.outputColorSpace = SRGBColorSpace`。トーンマッピングは原則 `NoToneMapping`（2D画像の色をそのまま出す。和風ダークの色設計をテクスチャ側で完結させ、ACES等で沈ませない）。仮にBloomを足す場合のみ後述のpost層で対応。
- 1フレームの描画はワールド→エンティティ→FX→（UIはThree.js外のDOM/HUD層）の順。

#### A1-2. オルソカメラ（角度 / ズーム）
- `THREE.OrthographicCamera` を斜め固定。透視ゆがみゼロでアイソメの一貫した見た目を保証する（タイル・地面の平行を保つ）。
- カメラ角度（00 §5裁定で確定。yaw のみ要実機調整）:
  - 方位角 yaw = 45°（クラシックアイソメ。タイルが菱形に見える）。
  - **仰角 pitch = 30°固定（確定・裁定）**。スプライト正面の視認性を優先（理由: 35.264°だとビルボード上端が遠近で潰れて顔が見えにくい）。35.264°（真アイソメ）案は撤回。**この30°固定をC6スプライト原画のアングル基準として通達**（C6はこの仰角に整合したコマを生成する）。
  - カメラは常にこの角度のままターゲット（プレイヤー）を中点に平行移動のみ（回転しない＝方向アニメ数を有限にできる、後述A1-3/リスク）。
- ズーム/可視範囲（仮値）:
  - 基準解像度（内部レンダリング）: 1280×720。表示はCSSで等比フィット。
  - 可視ワールド幅 = 約20ワールドユニット相当（キャラ身長を約1.8ユニットと置くと、横に約11人分が映る画角）。`camera.zoom` で調整、`updateProjectionMatrix()` を必ず呼ぶ。
  - frustum: `left/right = ±viewW/2`, `top/bottom = ±viewH/2`, `near=-1000, far=1000`（オルソは near 負値可。深度レンジを広く取り z-sort 余裕を持たせる）。
- ピクセルスナップ: カメラ移動量を内部解像度のピクセル境界に丸める（デウスの教訓「非整数縮小でスプライトが滲む／揺れる」をカメラ側でも防止。`Math.round` でカメラpan後のスクリーン位置をピクセルグリッドへ吸着）。

#### A1-3. ビルボードスプライト方式（中核判断）
- 全キャラ/構造物は `PlaneGeometry` + `MeshBasicMaterial`（または `SpriteMaterial`）＋アルファ抜きPNG/WebP。
- **常時カメラ正対は不要、かつ採用しない**。判断と理由:
  - カメラは回転しない固定アイソメ。よって「カメラへ毎フレーム向け直す（`lookAt`）」処理は不要。
  - 板ポリは**ワールドに対し固定の傾き**で立てる（地面に対して垂直＝Y軸up、ただしカメラ仰角ぶんだけ手前に倒したビルボード傾き）。具体的には板を「カメラの上ベクトルと右ベクトルが張る平面」に一度だけ合わせて固定。カメラが動かないので毎フレーム再計算しなくてよい。
  - これにより `THREE.Sprite`（常時正対）ではなく、固定回転の `Mesh` を使う。理由: Sprite は深度ソートが座標基準でなく描画順依存になりがちで、多数表示時のz破綻を招く。固定Meshならz座標で素直にソートできる。
- スプライトの「向き（facing）」は**テクスチャ差し替え**で表現する（板自体は回さない）。**方向数=4で確定（down/left/right/up、00 §5裁定）**。**右向きは左向きの水平反転（flipX＝UV反転 or scale.x=-1）で生成**し、別テクスチャは持たない（実質3向き素材で4facingを賄う。8方向は撤回）。
- アルファ:
  - `material.transparent = true; material.alphaTest = 0.5`（半透明縁のソート問題を避けるためアルファテストを主、ブレンドは縁のみ）。
  - 半透明（霊・式神の透過表現）が必要な個体のみ `depthWrite=false` の専用マテリアルに分離し、`fxGroup` 側で最後に描く。
- アンカー: 板の原点は**足元中心（下端中央）**。理由: 深度ソートと接地影・足元判定（A2移動）が足元基準で統一できる。デウスの「object の y は足元基準、footprint は上方向」を踏襲する。

#### A1-4. 深度ソート（z）
- 「奥にいるものほど先に描く」をワールド座標で決定する。アイソメでは画面の上＝奥なので、**スクリーン深度 = (worldZ - worldX)** 系の合成値（カメラ向きへの射影）で各エンティティの描画優先度を毎フレーム算出。
- 実装方針（2択。両方を要件として明記、初期はBを採用）:
  - A: `renderer.sortObjects` に任せ、各Meshの `material.depthTest=true` ＋ z位置をそのまま深度に使う。オルソ＋固定板なので素直に効く。
  - B（採用）: `entityGroup` の子を毎フレーム「足元のスクリーン深度」で明示ソートし `renderOrder` を連番付与。`depthTest=false` で重なりは描画順で決める。**理由**: 半透明ビルボードが混ざると depthTest だけでは縁が抜ける／チラつくため、明示ソートの方が破綻が少ない（デウスのビルボード経験を踏襲）。
- 同一足元z（重なり）時の安定化: 第二キーに `entityId`（生成順固定ID）を使い、フレーム間でソート順が揺れない（チラつき防止）。
- 受け入れ基準: プレイヤーが構造物の前後を歩いたとき、前後関係が1フレームも逆転しない。NPC同士が密集しても描画順が毎フレーム入れ替わってチラつかない。

#### A1-5. ライティング / 霧（和風ダークの空気）
- ビルボードは `MeshBasicMaterial`（ライト無視）を基本とし、**陰影はテクスチャに描き込む**（デウス同様「絵が正」。3Dライティングで沈ませない）。
- 空気感は以下で作る:
  - `scene.fog = new THREE.Fog(color, near, far)`（仮: 紫を避け、藍墨色 `#10131c` 系。near=12, far=40 ワールドユニット）。MeshBasicでもfogは効く。遠景NPC/構造物が霧に溶けて「広く奥行きがある」MMO風の空気＋描画負荷の自然なフェードアウトを兼ねる。
  - エリアごとの環境カラー（昼の都／夜の都／妖魔の巣）を `fog.color` ＋ 画面オーバーレイ（後述post）で切替。
  - 任意の弱い `AmbientLight` は使わない（MeshBasicに無効）。「光源演出」は発光テクスチャ＋fxGroupの加算ブレンド板（提灯・鬼火・呪符の光）で行う。
- 禁止: 紫グラデーション基調（ユーザールール）。和風ダークは藍・墨・朱・金で構成。

#### A1-6. 影
- 本物のシャドウマップは**使わない**（負荷とビルボードの相性が悪い）。代わりに**接地影＝足元に敷く半透明楕円の板**（`shadowGroup`、地面に水平、`depthWrite=false`）。
- 影はエンティティの足元座標に追従。ジャンプ/浮遊する式神（鬼火系）は本体が浮いても影は地面に残す（高さに応じ影を薄く小さく）。
- 受け入れ基準: 全キャラに接地影があり、接地位置が一目で分かる（アイソメで高さが曖昧になる問題を影で補う）。

#### A1-7. 描画負荷方針（多数NPC同時表示）/ LOD / カリング
- 目標: NPC・敵・装飾ビルボードを画面内＋近傍で**同時150体**描画して 60fps（M2 16GB / デスクトップChrome基準＝v1の正基準）。モバイル（30fps許容・上限80体）はv2スコープの参考値（v1の受け入れ基準には含めない）。
- テクスチャアトラス: 同種スプライト（市民・雑兵・式神コマ）は1枚のアトラスにまとめ、`material` を共有してドローコールを削減。理想は同マテリアル個体を `InstancedMesh` 化（向き/コマはUVオフセットをインスタンス属性で渡す）。
- カリング:
  - フラスタムカリング: Three.js標準の `frustumCulled=true` を維持。
  - 距離カリング: カメラ中心から半径 R_cull（仮: 35ユニット＝fog far近辺）外のエンティティは `visible=false` かつ更新（AI・アニメ）も停止（A2/A3のエンティティ更新ループと連動）。
- LOD（仮・2段）:
  - 近（< 18u）: 通常スプライト＋歩行4コマアニメ＋接地影。
  - 遠（18〜35u）: 静止コマ（idle固定）＋影なし＋AI更新を低頻度（4フレームに1回）に間引き。
- 更新の間引き: 遠方/画面外NPCのAIは tick レート低下（後述A2のエンティティ更新と統一スケジューラで）。
- 受け入れ基準: 同時150体表示の町ハブで内部fps≥55（デスクトップ）。ドローコール数を計測し、同種スプライトは数十コール以内（アトラス/インスタンス効果）。

#### A1-8. ポストプロセス（最小限・任意）
- 既定OFF。必要時のみ `EffectComposer` で Bloom（鬼火・呪符の発光のみ強調）＋ Vignette（画面四隅を落として和風ダークの没入）。ChromaticAberrationは入れない（デウス系の知見＝コスト高）。
- post を入れる場合、内部解像度を 1280×720 から落とさず、Bloom は閾値高め（発光テクスチャだけ拾う）。

### 受け入れ基準（A1）
- オルソアイソメで世界が平行投影され、カメラ回転なしで前後関係がz座標どおり描画される。
- ビルボードは板を回さず、向きはテクスチャ差替で4方向（down/left/right/up）表現できる。right は left の flipX 反転で出る（別テクスチャ無し）。常時 `lookAt` を呼んでいない（固定回転）。
- 半透明・不透明が混在しても深度破綻（縁抜け・チラつき・前後逆転）が起きない。
- fogとvignette（任意）で和風ダークの空気が出る。紫グラデを使っていない。
- 全キャラに接地影。シャドウマップ未使用。
- 町ハブで同時150体・内部fps≥55（PC）。同種スプライトのドローコールがアトラス/インスタンスで圧縮されている。

## A2. 移動・操作・カメラ追従

### 目的 / スコープ
リアルタイムアクション戦闘に耐える操作系を定義する。移動・攻撃・回避・呪術・式神切替の入力、ピクセル/小数のどちらで座標を持つか、衝突、カメラ追従を確定する。デウスの「ピクセル移動・整数スナップ・スプライト一貫性」教訓を継承しつつ、アクション戦闘向けに整える。

### 詳細要件

#### A2-1. 移動方式（クリック移動 vs WASD → WASD推奨）
- **採用: WASD / 矢印キー（4方向入力＋斜め同時押し許容・向きは4方向に丸める）＋ゲームパッド左スティック。クリック移動は採用しない。**（00 §5裁定: スプライトの向きは4方向。移動入力は斜め同時押しを許容するが、`facing` は4方向へ丸める＝05-maps §1.3と一致）
- 理由:
  - リアルタイムアクション（回避・間合い管理）はクリック移動だと操作遅延・経路探索依存で破綻する。直接入力が必須。
  - デウスはピクセル移動の直接操作で成立しており、操作系の知見を流用できる。
- 移動はワールド座標を**小数(float)で保持**し、**描画時のみ整数（内部解像度ピクセル）へスナップ**（デウスの「`Math.round` で整数スナップ」をレンダリング段で踏襲、内部の物理は小数で滑らかに）。
- 入力ベクトルはカメラ基準（画面の上＝アイソメの奥）へ回転変換してワールド移動量にする（WASDの「上」が画面上＝ワールドの奥になるよう yaw 45°ぶん回す）。斜め入力は正規化して斜め移動が速くならないようにする。
- 移動速度（仮）: 歩行 3.5 u/s、ダッシュ無し（アクションなので回避ロールで緩急）。式神追従は後述。

#### A2-2. 衝突
- 衝突は**2Dトップダウングリッド/矩形**で行う（z高さは描画専用、当たりはXZ平面）。デウスの walkable/blacklist 思想を継承し、**「非可動域（壁）矩形リストのみ」を持つブラックリスト方式**（保守性優先、デウスの最終結論と同じ）。
- プレイヤーは半径 r（仮 0.35u）の円としてXZ平面で矩形群と衝突。壁ヒット時は壁に沿ってスライド（アクションの操作感）。
- マップ外チェック必須（デウス教訓: 全域可動だとマップ外が「壁なし＝歩ける」になりスポーンが画面外へ。ワールド境界矩形を明示）。

#### A2-3. アクション戦闘の操作
- 入力（キーボード既定 / 同時押し対応）:

（00b §7.4 ホットバー8スロット⇄B1入力 対応表に整合。主人公は直接近接で殴らない＝手段は符＋呪＋式神＋鎮魂。MP相当は「気」。00b §2.5 / §7.4 が正典）

> 注: キー1/キー2/E/J/K/L/Q/鎮魂窓 の割当は 00b §7.4 ホットバー8スロット対応表と一致させること（B7描画・B1入力の正典）。

- 攻撃・呪術・回避は**フレーム駆動のステートマシン**（idle/move/attack/dodge/cast/hurt/down）。各状態は遷移可能フラグ（例: 攻撃中は移動入力を受けるが向き変更のみ等）を持つ。実装はA1の `frame`/`facing` と直結。
- ヒットボックス/ヒット判定はXZ平面の矩形 or 扇形（攻撃の前方判定）。判定はB1戦闘モジュールが消費するが、A2は「入力→アクション状態→向き＋当たり領域の発生位置」までを供給する責務。
- 入力バッファ（仮100ms）: コンボ・回避先行入力を受ける（アクションの操作感）。

#### A2-4. カメラ追従
- カメラはプレイヤーを中点に**平行移動のみ**（回転・ズーム変化なし）。
- 追従はデッドゾーン付きスムーズ追従: プレイヤーが画面中央の小矩形（仮 ±2u）を出たぶんだけ、`lerp`（仮 t=0.12/frame）で寄せる。急停止/方向転換でカメラが揺れすぎないよう上限速度を設ける。
- カメラ位置は最終的にA1のピクセルスナップへ通す（小数追従→描画時に整数化。これをしないと背景に対しスプライトがサブピクセルで滲む＝デウスの滲み教訓）。
- マップ境界クランプ: 小マップではカメラが世界外を映さないよう端でクランプ（カメラ可動域 = ワールド矩形 − 画面半分）。
- 戦闘/ボス時の任意カメラズーム（仮）: ボス戦のみ `camera.zoom` を緩やかに引く演出フックを用意（既定はフィールドと同一）。

#### A2-5. 式神の追従/切替（移動レベルの責務）
- 主人公＋使役式神（**縛＝v1は1枠固定＝同時召喚1体**。複数枠はv2。00 §5裁定）が**自律追従**（プレイヤーから一定距離で隊列追従、stepTowards的な意図駆動移動。デウスのNPC歩行恒常化＝閾値判定を廃した意図駆動移動を踏襲して「ふわふわ浮き」を回避）。
- 召喚/帰還（ホットバーのキー1＝玄）＝召喚枠のオン/オフ、切替（E・順送り）＝アクティブ式神の入替（v1は1体のため実質無効、v2で意味を持つ）。キー割当は 00b §7.4 ホットバー対応表に一致させる。戦闘ロジックはB1だが、A2は式神エンティティの**移動・追従・向き・コマ送り**を供給。
- 式神は壁・段差で詰まらないよう、追従が一定時間滞ったらプレイヤー近傍へワープ（テレポート）でリカバリ（経路探索は持たない＝単機・軽量）。

### 受け入れ基準（A2）
- WASD/スティックで滑らかに歩け（4方向入力＋斜め同時押し許容・向きは4方向に丸める）、斜めが速くならない。入力の上がワールドの奥になる。
- 壁にぶつかると沿ってスライドし、マップ外へ出られない。
- 攻撃/回避/呪術/式神切替が同時押し・先行入力込みで破綻なく状態遷移する。回避に無敵フレームがある。
- カメラがデッドゾーンでスムーズ追従し、端でクランプし、スプライトがサブピクセルで滲まない（描画整数スナップ確認）。
- 式神が意図駆動で追従し「ふわふわ横滑り」せず、詰まってもワープで復帰する。

## A3. ワールド・シーン管理・遷移・セーブ

### 目的 / スコープ
ゾーン（門前町＝ハブ／野（フィールド）／ダンジョン）のロード・遷移、エンティティ生成・管理ライフサイクル、localStorageセーブ/ロードのスキーマを確定する。デウスの「遷移spawnの座標系・ゲートフラグの正準・3スロットセーブ・封筒スキーマ・migrate」教訓を全面踏襲する。

### 詳細要件

#### A3-1. ゾーン構成とロード
- ゾーン単位＝1マップ（門前町ハブ / 各フィールド / 各ダンジョン階層）。v1（第1章縦スライス）は「門前町1＋フィールド1＋ダンジョン1＋ボス1」。
- **シームレスではなく区切り（明示遷移）を採用。** 理由:
  - 単機ブラウザ・3Dモデル無し・多数ビルボードで、オープンワールド級のストリーミングはコスト過大。デウスもゾーン区切りで成立。
  - ゾーン境界に「出口（exit）トリガー領域」を置き、接触で次ゾーンへ。ダンジョン入口/家屋など一部は autoEnter（歩き込みで自動遷移、向きゲート付き）。
- マップ定義はデータ駆動（JSON/JSモジュール）: `mapId`, 背景/地面テクスチャ, ワールドサイズ, 障害物（壁矩形 blacklist）, 出口リスト, NPC/敵/拾得の配置, BGMキー, 敵シンボル配置（**エンカウント=同一シーン内のシンボル接触**で field 内の battle サブ状態へ。専用バトルマップへ遷移しない。00 §5裁定。B1/B2連携）, area種別（town/field/dungeon/boss）。

#### A3-2. 遷移（exit）の座標規約（デウス教訓を正準化）
- 出口（exit）は **{ to(行先mapId), rect(トリガー領域), direction(進入方位), spawnX/spawnY(行先での到着点), requireFacing(autoEnter時の入店向き), requiredFlag(施錠), autoEnter(bool), visible(描画有無) }** を持つ。
- **座標系を最初から二系統に分けて固定し、混同を禁止**（デウス最大の事故源）:
  - 出口トリガー rect・到着点 spawnX/Y は **ベース座標（worldScale適用前）** で保持。
  - 描画/衝突に使う際にロード時 ×worldScale して **ワールド座標** にする処理を1箇所（`prepareMap`）に集約。
  - 「トリガー領域＝そこへ歩くと遷移」と「到着点＝spawn」は**別物**（デウスの誤一般化を踏襲しない）。
- 到着スポーンは「来た扉の内側エッジ＋最小オフセット＋歩行可スナップ＋マップ内向きfacing」の**戻り扉アンカー**を既定とし（デウス最終決着＝f781398の方式）、手置きspawnは片道/特殊遷移のフォールバック。
- autoEnterドアは「requireFacingの向きで・手前側からの接近のみ・戸口幅に整合」した帯判定で発火（横切り誤入店ゼロ、デウス 9c271aa/2601869 の確定仕様）。
- **バウンス防止**: 到着スポーンが行先出口ゾーン内に入らないこと（クールダウン後に押し戻される事故）。ロード時バリデータで全遷移を機械検査（デウスの full_audit 相当を要件化）。

#### A3-3. ゲート（進行ロック）
- 出口に `requiredFlag` を持たせ、`storyFlags` で評価（B5クエスト連携）。施錠機構をデッドコードにしない（デウス教訓: lock定義0件で開幕ラスボス直行可能だった）。
- v1第1章は最低限のフラグゲートのみ（例: 羅城門・地下の奥扉は `shikiUnsealed`＝封印解除イベント済フラグでゲート。00b §7.2/§7.3 のフラグ名・QUEST_STEP に一致させる。玄の契約自体はプロローグ既済のため「式神入手ゲート」ではなく封印解除イベント基準）。
- ゲートフラグの正準保管先を1ファイルに固定（デウス: map-objects-data.js が正準、map-system.js の exit はロード時上書きで死にコードという罠を回避）。本プロジェクトは「マップ定義データファイルが正準、ランタイムは読むだけ」と最初から決める。

#### A3-4. エンティティ管理（ライフサイクル）
- ゾーンロード時にマップ定義から **エンティティを生成**（プレイヤーは永続、式神はパーティ状態から復元、NPC/敵/拾得はマップ定義から生成）。
- 退出時にゾーン固有エンティティを破棄（Three.jsの `geometry/material/texture` を共有アトラス以外は `dispose`、メモリリーク防止）。共有アトラス/共通マテリアルはアンロードしない。
- 更新スケジューラ: 全エンティティの tick（AI・アニメ・移動）を一元管理し、A1の距離カリング/LODと連動して画面外/遠方を間引く。
- エンティティIDは生成順固定（A1の深度ソート第二キーと共通）。

#### A3-5. セーブ / ロード（localStorage スキーマ）
- デウスの確定方式を踏襲: **メタ封筒 ＋ 3スロット ＋ migrate ＋ 書出/読込（ファイル）**。クラウドは静的Pages前提で後付け（storage差替式に設計）。
- スロットキー: `kyoonto_save_1 / _2 / _3`。封筒:

```
{
  version: 1,
  timestamp: <ms>,
  state: { ...ゲーム状態 },
  meta: { location, level, partyShikigami, chapter, playTime, timestamp }  // ロード一覧の表示用
}
```

- `state`（v1スキーマ・各モジュール所有を集約）:

| キー | 所有モジュール | 内容 |
|---|---|---|
| player | A2/B2 | { x, y, facing, hp, ki, level, exp, kegare } ※MP相当は「気(ki)」に統一（旧mp廃止）。穢ゲージ(kegare 0-100)を保存。座標はベース系で保存しロード時スナップ。速等は再導出（00b §2） |
| currentMapId | A3 | 現在ゾーン |
| shikigami | B1/B2 | 使役式神の配列（id, level, exp, 習得呪術, 装備） |
| inventory | B3 | 所持品・装備 |
| gold | B4 | 所持金（通貨=**文(もん)**・単一整数 `save.gold`。旧 `save.zeni`／「銭」表記は廃止。00b §1） |
| storyFlags | B5 | 進行フラグ（ゲート/イベント/oneTime） |
| quests | B5 | クエスト進捗 |
| settings | A1/A2 | 音量・キーコンフィグ等 |

- 規約:
  - 座標は二重スケール事故防止のため**ベース座標で保存**（デウス: serializePlayerはx/yをスケール無しで保持→ロード時 findSafeSpawn でスナップ）。
  - `state` にマップのNPC/壁等の動的配列は含めない（マップ定義から再生成。デウス: maps[].npcs を直列化しない）。
  - 読込時 `validateEnvelope`（version/構造チェック、壊れ/版違いは null）、`migrateLegacySave`（旧キー→スロット1へ冪等）、ロード後は battle状態を防御的に解除し、保存座標が壁内なら歩行可へスナップ。
- ゲームオーバー時は3スロット＋New Gameのロード画面（閉じられない＝続行バグ防止、デウス確定仕様）。
- セーブ手段（00 §5裁定で確定）: **宿屋でのオートセーブ＋井戸での手動セーブ**を正とする。宿屋は霞ヶ辻（Z01）に配置し、宿泊時にオートセーブ（穢の休息減少も兼ねる）。井戸は手動セーブ点。加えてファイル書出（Blob DL）/読込（file input→validate→スロット選択）を提供。**ゾーン遷移時のクイックセーブはv2スコープ**（v1は宿屋オート＋井戸手動のみ）。

#### A3-6. BGM / シーン状態（デウスのBGM教訓を予防的に要件化）
- BGMは**世代トークン方式で直列化**（フィールドBGM予約と戦闘BGM開始が同フレームで競合し残留する事故をA3の状態遷移設計で根絶。`changeFieldBGM` は battle中は無視等）。
- アセット未配置でも無音継続（エラーで止めない）。
- シーン状態 `currentScene ∈ {title, field, battle, menu, event, gameover}` を単一の正準フラグで持ち、入力ルータ・更新ループ・BGMがこれを参照（デウスの「複数フラグ競合でロック」事故を回避）。
- **`battle` は `field` 内のサブ状態であり、マップ遷移を伴わない（00 §5裁定）**。エンカウントは同一シーン内のシンボル接触（フィールド配置の敵シンボルに触れる）で、同じマップ・同じカメラのまま戦闘サブ状態へ入る（戦闘専用マップへロードしない）。`battle` 中は移動・遷移・通常入力ルータを戦闘ルータへ切替えるが、`currentMapId` とエンティティは保持。戦闘終了で `field` へ戻す（マップ再ロード無し）。B1/B2戦闘モジュールはこのサブ状態の中で動く。

### 受け入れ基準（A3）
- 門前町→フィールド→ダンジョン→ボス→戻る、の全遷移が、到着点ズレ・押し戻し（バウンス）・壁埋まり・画面外スポーンなく成立する。
- exit のベース/ワールド二座標系が `prepareMap` 1箇所でのみ変換され、トリガーと到着点が別管理されている。
- 進行ゲートが requiredFlag で機能し、未入手で奥へ進めない／入手後に開く。フラグの正準保管先がデータファイル1つに固定。
- ゾーン退出でエンティティが dispose され、長時間プレイでメモリが線形増加しない。
- 3スロットセーブ/ロード/書出/読込が往復整合し、壊れ/版違い封筒を拒否、旧版を冪等migrate。座標がベース保存で二重スケールしない。
- ゲームオーバー画面が閉じられず、ロードまたはNew Gameのみで復帰する。
- BGMがゾーン/戦闘で切替わり、戦闘→フィールド復帰で戦闘曲が残留しない。

## 依存関係
- **A1 → A2/A3 が依存**: 描画契約（ビルボード/深度/カメラ/座標系）はA1が供給し、A2の移動表示・A3のエンティティ生成が乗る。
- **A2 ↔ A3**: A2の移動・衝突はA3のマップ定義（壁blacklist・ワールド境界・出口）を消費。式神追従はA3のエンティティ管理に乗る。
- **A2 → B1戦闘**: A2は入力→アクション状態→向き＋当たり領域発生位置までを供給、ヒット解決はB1。式神の戦闘ロジックはB1（A2は移動/追従/向き/コマのみ）。
- **A3 → B2/B3/B4/B5**: セーブ `state` スキーマは各システムの所有データを集約。ゲートフラグはB5の進行と一致させる。
- **A3 → B7/UIPanel**: メニュー/ロード/ゲームオーバー画面はB7のUIPanel（固定枠＋ページ送り、webスクロールバー厳禁＝デウスUI統一思想）を使う。本基盤はその入力ルータ（`if(UIPanel.isOpen()) return UIPanel.handleKey(e)` を中央keydown先頭に）の配線位置を規定。
- **C6アセット・パイプライン → A1**: スプライトアトラスの命名規則・セル整列（同一足元y/中心x/セルサイズ）はC6が生成、A1が規約として要求。
- **C5マップ・ゾーン設計 → A3**: マップ定義データ（座標・出口・配置）の形式はA3スキーマに従う。
